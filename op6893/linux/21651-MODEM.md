# 21651 基带推进记录

21651 与 20615 同 SoC、同 `op6893` 机型名，但项目号不同。本机刷的是
20615 的 LK 与 DTBO，`md1img` 的版本串也同为 `K6893V1_64_K419_20615S`
（2024/01/08），但整分区 SHA-256 与 20615 不同——是同一发布版本的另一个
构建。

## 与 20615 的差异

- **共享内存 cached bank 不同**：本机 LK 给的是
  `0x8a000000+0x2960000`，板级文件里写的是 `0x88000000+0x4960000`。
  驱动使用 LK 的值，`lk_regions` 可直接读出。
- **NVRAM 必须用本机的**。首次尝试复用 20615 的私有工作副本，MD 在
  `mcu/service/nvram/src/nvram_main.c:3414` 断言
  （`ex_type=80`，`ASSERT_FAIL_EXCEPTION`）。迁移记录里已经写明
  "不复用 20615 私有数据"。
- 用本机 NVRAM 后该断言消失，MD 继续走到 CCISM。

## 取本机 NVRAM

`21651/extract-nvram.sh <输出目录>` 在主线上只读挂载四个分区并打包，
不改动设备：

```
Z <- nvdata/md    X <- protect1/md    Y <- protect2/md    S <- nvcfg
```

本机快照 452 个文件，放在 `/data/src/op6893-private/nvram-21651-20261122`。
它带 `.op6893-fs-working-copy` 标记和 `streams.sha256`，与 FS provider 的
驱动器映射一致。

## 已解决的阻塞点

2026-11-22 的三轮推进把 FS/RPC 侧全部补齐，MD 现在能消费 5983 笔应答：

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| `0x100c Move ... status=-16` | MD 复用参数缓冲：目标路径在终止符之后残留上一笔 `FindFirst` 的模式串 `Z:\NVRAM\BACKUP\FILE*`，后端把整段当路径，遇到内嵌 `:` 判为非法 | 宽路径参数按厂商的 C 字符串语义处理，只取第一个终止符之前的部分（`8cca63f02`） |
| 后端抛 `UnsupportedOperation` 后停服 | `0x100f` 是 `FS_CCCI_Delete`，此前没有实现；未实现的用户 RPC 也直接以传输层错误拒绝 | 补上 `0x100f`（单文件 `unlink`，目录按厂商语义返回 `-18`）；未实现的 RPC 回厂商的单个 `NO_OP=-1` |
| MD 在 `mml1_rf_error_check.c:211` 断言，`para=0xf0f0f0f` | `0x4009` GPIO/ADC 复合查询由内核独占，`ccci_rpc_provider_reply()` 直接返回 `-EOPNOTSUPP`，整个 submit 失败 | 在内核 provider 实现 v1/v2 记录；电平由平台驱动从 `band-strap-gpios` 采样一次后交给 provider |

`0x4009` 的板级事实：本机 `band-strap-ids = <63 64 65 66>`，用 GPIO
chardev v2 直接读到的电平是 **`63=1 64=0 65=1 66=0`**（不是从别的机型日志
推断的；21609 的厂商日志恰好也是这个组合，但那只作旁证）。

## 原 60 秒镜像上的阻塞

MD 的早期 NVRAM 阶段比 20615 长得多（约 40–50 s、约 6000 笔请求），走完后
在 CCISM 里断言，HS2 始终没有到来：

```
handshake  state=6 error=-110 hs2_seen=0
dispatch   state=7 error=-110
services   tx=5983 tx_error=0
ccism      state=1 (ARMED) md_open=1 scp_open=1
md_ee      ex_type=80 class=assert line=2031
           path=mcu/driver/ccismcore/src/ccismcore_ccci.c
           para=0x4,0x9eeca80,0x0 lr=0x90103244
```

已排除的解释：

- **不是特性集不足**。当前树的 `ccci_runtime_profile.c` 已含 20615 修好
  HS2 时那 28 项（`profile_aux` 的 5/7/8/9/10/11/12/16/19/20/25/32 加区域
  项）。20615 那次"9 项 → MD 死在 `MPU_NOT_ALLOW`"的结论在 21651 上不适用。
- **不是 feature 15**。按 20615 的结论把 `runtime_mask` 设成 `0x8000`
  抑制 `CCB_SHARE_MEMORY` 后，`negotiated` 串与断言点完全不变。
- **不是 Python 太慢**。设备上实测 `respond()` 单笔 0.13–0.20 ms；整轮
  约 6000 笔的往返约 8.6 ms/笔，瓶颈不在用户空间（开/关 tracing 只差 2%）。
- **不是 FS 语义错误**：NVRAM 备份轮转、`Restore`、`CMPT_Read`、目录属性
  都在推进，MD 一直在消费应答直到它自己断言。

也就是说：MD 走完 NVRAM 之后没有发 HS2，而是在 CCISM 侧断言。厂商内核只在
**MD READY（即 HS2 之后）**才发 `CCISM_SHM_INIT`（`ccci_fsm_scp.c` 的
`ccci_scp_md_state_sync_work`），所以 CCISM 停在 ARMED 符合未收到 HS2 的状态机行为，不能据此认定需要提前发通知。
下节的时间线复测区分了 AP 超时与 MD 断言。

## 同镜像时间线复测（2026-11-22）

在交接镜像 `bf791ade3885` 上，两轮均先重启 AP，用同一份 21651 NVRAM
快照，并以约一秒的间隔读取握手、服务计数及异常头。异常区可跨 AP
重启保留；本轮只把 CPU 放行后从 `-ENODATA` 转成可解码的异常算作新断言。
下表时间为 AP uptime，精度约一秒。

| 世代 | AP 侧事件 | MD 异常区 |
| --- | --- | --- |
| 21652（未加载 RPC 策略，作为对照） | 约 14.18 s 进入 WAIT_HS2；39.54 s 已报 `-EPIPE`，后端以 `UnsupportedOperation` 退出，已提交 2880 笔应答 | 102.04 s 首次读到新的同文件同一行断言，参数变为 `0x1,0x9eee8c0,0` |
| 21653（按交接配置加载策略） | 约 14.21 s 进入 WAIT_HS2；73.88 s 已报 `-ETIMEDOUT`，共提交 5811 笔应答，未见 HS2；期间一度见 `tx_error=-16`，之后计数继续增长，最终为 0 | 截至取证后关电，异常头仍返回 `-ENODATA` |

两轮 RAW_DFD 全区 8 MiB 都是零。21652 说明该断言可以出现在 AP 服务
已经终止之后；21653 则确认有限的 60 秒窗口内确实可先发生 AP 超时。
这些数据不能确定交接那次参数为 `0x4` 的断言与 AP 超时的先后，
也不能证明 21653 若继续持电就一定不会断言。主线当前的 60 秒 deadline
会停止服务，仍需用只影响 21651 试验镜像的有界长窗口做单变量对照，
记录最后一笔服务、超时、异常头落地和 HS2。厂商 4.19 与 6.6 源树的
通用 `BOOT_TIMEOUT` 宏是 30 秒；延长主线窗口是诊断手段，不是已证实的修复。

采集脚本：`mt6893-direct/21651/md-hs2-timeline.sh`；主机私有日志：
`21651/hs2-evidence.DQlSih/`、`21651/hs2-evidence.oRSJkQ/`。
实测后设备仍在原镜像，systemd 正常，MD 与 SCP 均已停止。

`drivers/misc/Makefile` 只在连接栈或 CMDQ 扩展启用时进入相关目录。

## 构建

```
21651/build.sh userdata radio graphics systemd normal <modem>
```

`<modem>` 取 `off`（默认，禁止任何 CCCI 配置）、`inspect`（只读 LK 交接）、
`platform`（冷电源 owner）、`full`（SCP/CCIF/握手/服务/CCISM/DPMAIF）。

`platform` 与 `full` 会选用
`mt6893-op6893-21651-modem.dts`，它打开 MD1 域、PMIC 供电、平台 owner、
SCP owner/observe 与 DPMAIF，并关闭 `modem-handoff`——两个 owner 不能同时
快照 LK tag 缓冲区，否则第二个 probe 在 `snapshot` 阶段返回 `-EBUSY`。

## 上机顺序

```sh
S=/sys/devices/platform/10724000.scp-resource-hold
P=/sys/devices/platform/10209000.modem-platform
echo 26m   > $S/pin
echo start > $S/runtime
echo takeover > $P/md_power
echo on       > $P/md_power
# 启动 FS/RPC 后端后再放行
echo prepare <gen> > $P/md_boot
echo release       > $P/md_boot
# 收尾
echo off  > $P/md_power
echo stop > $S/runtime
```

主机侧编排用 `md-release-cycle.py`（`OP6893_SSH=21651/ssh-usb.sh`，
`--root` 指向本机快照）和 `md-release-run.sh`。
